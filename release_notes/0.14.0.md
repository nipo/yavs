yavs 0.14.0 fixes a silent wrong result in Cranelift-compiled code, makes every release archive profile-guided, and rejects more code that the standards do not allow. The x86_64 archives now need an x86-64-v3 CPU; each has a `-compat` archive that runs on any x86-64 CPU.

- **Silent wrong result fixed (#1089):** compiled code could use a constant in place of an operand of an array operation; the same code is in 0.13.0. Read the bug fix entry for who is affected and what we did not measure.
- **Breaking, x86-64-v3 archives:** the Linux and Windows x86_64 archives need AVX2 and the rest of x86-64-v3; the `-compat` archives run on any x86-64 CPU.
- **Breaking, stricter checks (#1084, #1085, #1086):** a label that repeats a declaration of its region, a declaration named `guard` in a guarded block, and an index constraint of the wrong type are now errors, with no `--relaxed`.
- **Profile-guided archives:** every archive is trained on its own platform; runs took about 6 to 10 percent less time on our measured designs, with large differences per design and two known slower cases.
- **Runaway loops (#1087):** a process or loop that never waits is reported as `E3009` in every tier instead of hanging under `--tier=clift`.
- **Archive README:** each archive has a generated `README.txt`, and `yavs --version` prints a `Build:` line.


# Breaking changes

- A statement label that repeats a declaration of its own declarative region is now error `E1101` (LRM 2008 10.1, 11.1, 12.1, 12.3: a label is declared in the enclosing process, subprogram, block, generate, architecture or entity, and two homographs may not be declared in one region). This covers a sequential label against a variable, constant, type, subprogram or parameter of its process or subprogram, even inside a loop; a concurrent label (process, block, generate, instance, assertion, assignment, procedure call) against any declaration of its architecture, block or generate, a port, a generic or a generate parameter; and a label in an entity's statement part against a declaration or a label of its architecture. Rename one of the two. A homograph in a nested region still only hides, so a signal of the architecture and a label in one of its processes or blocks may share a name. There is no `--relaxed` for this. (#1084)
- An explicit declaration with the name of the implicit signal `GUARD` of a guarded block (a signal, generic, port, constant, type, subprogram or alias called `guard` in the block) is now error `E1101` (LRM 2008 11.2, 12.3: the implicit signal is not a predefined operation, so an explicit homograph does not hide it). Rename the declaration. There is no `--relaxed` for this. (#1085)
- An index constraint whose discrete range has another type than its index is now error `E1300` (LRM 2008 5.3.2.2: the type of each discrete range is the type of its index). This covers a type mark, a subtype, `t range a to b` and a range attribute, for example `sv(severity_level)` for an array indexed by `natural`; before, the declaration was accepted and a later use failed with a misleading error. Use a range of the index type. There is no `--relaxed` for this. (#1086)
- The x86_64 release archives (Linux and Windows) now need a CPU with AVX2 and the rest of x86-64-v3 (Intel Haswell, 2013, or AMD Excavator and Zen, or newer); on an older CPU `yavs` says which features are missing and exits with status 1. Each release also has a `-compat` archive for the two x86_64 platforms (`yavs-<version>-x86_64-unknown-linux-gnu-compat.tar.gz`, `yavs-<version>-x86_64-pc-windows-msvc-compat.zip`) that runs on any x86-64 CPU, and a build from source does too; the aarch64 archive is unchanged.

# Features

- Every release archive carries a short `README.txt` with its version, target and CPU variant, its files and how to start; it replaces the project `README.md` that the archives held before. `yavs --version` also prints a `Build:` line on its second line: `x86-64-v3, AVX2 support`, `x86-64 baseline` or `aarch64`.
- Every release archive is now a profile-guided build, trained on bundled testbenches on its own platform and CPU level. On ten benchmark designs that the training never ran, measured on the GitHub runners that build the archives, a simulation run took about 6 to 10 percent less time than the same archive built without a profile (geometric mean over the designs, per archive 0.90 to 0.94 of the plain time), while analysis of a small file took the same time. The gain differs a lot per design: text I/O gained 14 to 25 percent, a design that spends its run in compiled code gained nothing, and one design (`rtl_bus`) took 4 to 6 percent longer on the Linux `-compat` archive for a reason we have not found. A design with a very wide out-port connection once took 2.3 times the instructions to elaborate before the training covered it, and another path the training does not run could do the same. These are runner figures, not figures for your machine; see the performance page. A build from source can do the same with `tools/pgo/build.sh` on Linux and Windows.

# Bug fixes

- A statement label with the name of an implicit predefined operation of its region, such as `minimum : process` next to `type t is (u, v)`, is accepted again, as LRM 2008 12.3 says, and hides the operation; a call of the operation after the label is an error. `fifo : fifo` with the component made visible by a use clause is still error `E1700`, which now says that the label hides the component and asks for the label to be renamed. (#1084)
- A process or loop without a wait statement whose loop ends in an `if` without an `else` is now reported as `E3009` (an infinite activation) in every tier; before, the run hung silently under `--tier=clift`, and the interpreter needed a thousand times the bound. (#1087)
- Fixed a silent wrong result in Cranelift-compiled code: when an array operation that the compiled code cannot do inline, such as filling more than 64 elements of a `std_logic_vector`, ran in a function that also assigns a constant late in its code, the operation could use that constant in place of its own operand, and the simulation went on with a wrong value and no message. The same code is in 0.13.0 (found by reading it, not by a failing user design). On the main branch before the fix it was reproduced under `--tier=clift`; at the default `--tier=auto` it was reproduced only on a development branch, and on a released build at the default tier it was not measured, so we do not know how often a 0.13.0 or earlier run is affected. If you ran 0.13.0 or earlier with compiled tiers and results matter, run again with 0.14.0 and compare, or compare against `--tier=interp`, which was not affected. (#1089)
